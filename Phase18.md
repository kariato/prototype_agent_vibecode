## Critique (UI is where invariants get accidentally violated)

Anti Gravity will be tempted to let UI “just write the file” or “just apply the patch.” That would destroy the entire trust model. UI must be a **thin controller**:

* sends intent + approvals + verification text
* renders artifacts + event stream
* never mutates workspace directly

---

# Anti Gravity Task Packet 09 — Gradio UI Panels + Wiring

## Goal

Build the **Gradio UI** as four panels wired to the runtime interfaces:

1. Documents Workspace
2. Diff Viewer
3. Runtime Console (event stream + checkpoint/proposal viewers)
4. Verification Panel (paste output + PASS/FAIL)

UI must:

* select/enter **absolute workspace root**
* initialize/load workspace state
* show current pending proposal + status
* allow approve/reject
* allow execute/resume graph
* allow record verification and resume
* show artifacts with links/paths + preview text

**No direct filesystem writes.** UI reads artifacts and calls runtime functions.

### Components

* File tree (documents only)

  * action type dropdown: Create / Rewrite / Append / CreatePhaseDoc

  * content textbox
  * “Submit Doc Proposal” button
* Proposal status box (current pending proposal summary)
* Approve/Reject controls (Gate A)

### UI Calls

* On browse/preview:

  * read file from workspace documents folder (read-only OK)
* On submit:

  * create docops proposal via registry submission helper
  * then run graph validate path if you prefer; simplest:

    * call `run_graph("/doc ...")` and let graph create proposal
* On approve/reject:

  * call proposal FSM transition + registry update
  * then `resume_graph()` if waiting

**Important:** do not execute docops directly in UI; execution happens when graph resumes.

## Safety Rules (Non-Negotiable)

* UI MUST NOT:

  * write documents
  * apply patches
  * delete anything
  * mutate artifacts directly
* UI can:

  * read documents for preview
  * read artifacts for display
  * call runtime functions for submit/approve/execute/verify
* UI must display “Recovery Required” banner if `scan_recovery()` returns issues
* UI must display current `pending_proposal_id` and `resume_node`

---

## Wiring Flow (What happens when user clicks)

### A) User types intent in Runtime Console

1. UI calls `run_graph(...)`
2. Graph creates/validates proposal and pauses at `await_approval`
3. UI shows proposal in Documents/Diff tabs

### B) User clicks Approve

1. UI calls `ui_approve(proposal_id)`
2. UI calls `resume_graph()`
3. Graph executes
4. Patch flow pauses at verification

### C) User records verification FAIL

1. UI calls `record_verification(...)`
2. Repair proposal created (awaiting approval)
3. UI calls `resume_graph()` → returns to awaiting approval for repair proposal
